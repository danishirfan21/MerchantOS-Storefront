## Cross-cutting findings

- **No anonymous catalog exists.** Rows 1-5 need a new customer-safe read surface (Recommended); changing `Catalog` to allow anonymous is not recommended because the same DTO carries SKU and exact stock.
- **Checkout is the largest gap.** The POS pattern is sound and can be copied, but the endpoint cannot be called by customers (Cashier-only) and encodes in-store assumptions (discount, tender, simulated card).
- **Order ownership today = staff `created_by`.** Any customer feature needs a new ownership key (Decision required).
- **Prices.** POS unit prices are ex-VAT and VAT is added by checkout; the Storefront shows whole-SAR prices and a "subtotal only, no tax" estimate. See `DATA_MODEL_GAP_ANALYSIS.md` for how to present backend amounts.
- **Verified absent:** CORS configuration in the POS API, any public-facing authorization policy, customer entity, channel field, delivery fields, fulfilment states.
- **Blocked by missing evidence:** live HTTP behaviour (nothing was run), POS Angular client contract usage, and the POS .NET test bodies.

## Contract mapping sketch (Recommended, not implemented)

| Storefront concept | Today | Backend-authoritative target |
|---|---|---|
| Product id | `p1`..`p25` | Public id or slug owned by the backend; POS `p01`..`p30` and SKU stay internal |
| Price | whole SAR number (`5199`) | `priceHalalas` integer, with an explicit VAT-exclusive/inclusive flag shown in the response |
| Stock | `in-stock` / `low-stock` / `out-of-stock` + optional count | Availability band derived server-side; no exact count unless low |
| Order id | `DEMO-XXXXXXXX` | Server-generated unguessable reference distinct from the internal UUID and `MOS-` number |
| Submission id | client `submissionId` (idempotency) | Reused as the client-supplied idempotency key, scoped server-side |
